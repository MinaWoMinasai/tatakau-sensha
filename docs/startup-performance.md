# 起動・ゲーム開始の待ち時間

通常どおり Release を起動すれば改善が有効になります。ゲーム設定や操作を変更する必要はありません。

## 特殊能力・工房統合後の回帰測定（2026-09-27）

同じPC・Release・`generated/startup-comparison/cache` を使用し、実装前後にWarm条件を各1回測定しました。測定中にビルドや別のゲーム実行は行っていません。

| 区間 | 今回の変更前 | 変更後 |
|---|---:|---:|
| タイトルの最初のフレーム | 3.634秒 | 2.285秒 |
| ゲーム開始要求→作戦マップ | 2.307秒 | 2.198秒 |
| 本編scene initialize | 1.491秒 | 1.414秒 |

秒単位の遅延の再発は確認していません。各1回の値なので、差にはOSのファイルキャッシュや実行ごとの揺らぎも含まれます。元データは `generated/abilities-startup-before/summary.json`・`warm.json` と `generated/abilities-startup-after/summary.json`・`warm.json` です。

生成量とキャッシュも変更前後で一致しています。未使用アリーナUIの生成省略2件、シェーダーディスクヒット40件、生成テクスチャヒット3件、RenderTexture122枚、カード装飾スプライト384個、graphics PSO47個・compute PSO4個です。新能力の線・リング・三日月は既存のネオン描画に追加し、既存の軌跡・音源・カード用HDR描画を再利用します。能力別のUI・描画ターゲット・テクスチャを起動時に追加生成していません。

`test_title_demo.ps1 -Configuration Release` も成功し、4段階の実戦デモ、フェード中の停止、新しい遠征への遷移を確認しました。特殊能力の実装とテストは `docs/tank-special-builds.md` を参照してください。

## 今回の実測（2026-09-26）

同一 PC・同一 Release 実行ファイルで各条件を１回ずつ測定しました。比較対象は `tank_game.project.json` のタイトルからローグライト本編への遷移です。

| 測定区間 | 従来処理 | 改善後・キャッシュ未作成 | 改善後・キャッシュ作成済み |
|---|---:|---:|---:|
| タイトルの最初のフレームまで | 12.082 秒 | 6.036 秒 | 1.899 秒 |
| ゲーム開始要求 → 作戦マップ表示 | 11.995 秒 | 2.148 秒 | 2.234 秒 |
| うち本編シーン初期化 | 8.198 秒 | 1.366 秒 | 1.456 秒 |

キャッシュ作成済みの起動は約 84%、ゲーム開始後は約 81% 短縮しました。ゲーム開始の値には演出用の約 0.65 秒も含みます。新規キャッシュ作成時は保存処理も含まれます。

実測データ: `generated/startup-comparison/summary.json`、`baseline.json`、`cold.json`、`warm.json`。ウォーム起動ではシェーダー 40 件、生成テクスチャ３件が全件キャッシュヒットしました。強化カードは全レア度の表示に備えたプールを起動時に確保するため、最初のカード表示へ大量の確保処理を先送りしていません。

初回の原因調査では旧進化 UI ２種が１シーンあたり約６秒、旧タイトルの破棄が約 3.5 秒、反射テクスチャの計算が約 1.8 秒でした。GPU ドライバーによる PSO 生成は 51 個合計で約 49ms だったため、今回は PSO の遅延生成や機種依存キャッシュの追加は行っていません。

## 変更した処理

- タイトルの戦闘デモとローグライト本編では、使わない旧アリーナの図鑑・進化画面２種・強化 HUD を生成しません。機体性能・進化経路のデータは読み込みます。アリーナではこれまでの UI を生成します。
- 強化カード３枚の装飾用スプライトを合計 1,500 個から 384 個へ削減しました。実際の HDR プレビュー付きカードで必要な最大数を、虹色・ホバー・取得演出を含めて検証しています。
- コンパイル済みシェーダーをファイルに保存します。ソース、include、コンパイル条件、コンパイラーが変わった場合は作り直します。既存のプロセス内キャッシュも保持しています。
- 決まった計算で作る反射・間接光用テクスチャを保存し、次回は計算結果を読み込みます。HDR の浮動小数点値、キューブマップ、ミップを保持します。
- 中身が空の描画用テクスチャは、最初から必要な状態で生成し、初期化だけのための GPU 送信・待機を減らしました。

画面の解像度、ブルームの強さ、軌跡、プレビューの描画品質、タイトルの戦闘デモは変更していません。

## 自分で測定する

Release ビルド後、`project/tools/measure_startup.cmd` を実行すると、従来処理・新しいキャッシュ未作成・キャッシュ作成済みの順で３回起動します。タイトルから通常のゲーム開始遷移を通り、作戦マップ表示後に自動終了します。比較用キャッシュは専用フォルダーに作り、既存のキャッシュは消しません。

PowerShell からは次のコマンドでも実行できます。

```powershell
./project/tools/measure_startup.ps1 -Configuration Release
```

結果はリポジトリの `generated/startup_measurements/<日時>/summary.json` と、処理ごとの JSON に保存されます。

- `titleSeconds`: WinMain に入ってからタイトルの最初のフレームを描画・送信し終えるまで。OS によるプロセス起動・DLL 読み込み時間は含みません。
- `gameStartSeconds`: ゲーム開始要求から作戦マップの最初のフレームまで。既存の約 0.65 秒のフェードも含みます。
- `sceneInitializeSeconds`: 本編シーンの初期化処理だけ。
- `processSeconds`: プロセス全体の実時間。起動・タイトル自動待機・フェード・終了も含むため、起動時間とは異なります。

PC の負荷、GPU ドライバー、ディスクの状態で時間は変動します。ここでの「キャッシュ未作成」は今回追加したキャッシュのみを指し、Windows・GPU ドライバーのキャッシュは削除しません。計測中は他のゲームやビルドを止めると比較しやすくなります。

## 通常起動でも原因を記録

通常起動時にも `project/generated/startup_trace.json` が作られ、シーン遷移後に更新されます。`events` に処理名と時間、`counters` にシェーダーのコンパイル数・キャッシュヒット数などを記録します。

`durationMs` は子処理を含む時間、`selfMs` は子処理を除いた時間です。親と子の `durationMs` を足すと二重計上になります。最初のフレームは `first_frame.TITLE`、本編は `first_frame.TANK_EXPEDITION` で確認できます。

| 環境変数 | 用途 |
|---|---|
| `CG2_STARTUP_TRACE=0` | 起動診断を無効化 |
| `CG2_STARTUP_TRACE_PATH` | 診断 JSON の保存先 |
| `CG2_STARTUP_CACHE=0` | 今回の改善を無効にして従来の初期化を再現する比較用設定。通常利用では指定不要 |
| `CG2_SHADER_CACHE_DIR` | コンパイル済みシェーダーの保存先 |
| `CG2_TEXTURE_CACHE_DIR` | 生成済み反射用テクスチャの保存先 |
| `CG2_STARTUP_AUTOTEST=1` | 起動比較スクリプト用。タイトルから本編へ進み、自動終了 |

キャッシュは再生成可能なデータで、セーブや調整値ではありません。破損・利用できない保存先の場合は通常の生成処理に戻ります。初回やキャッシュ再作成時は、２回目以降より時間がかかります。

既定の保存先は `project/generated/shader_cache/v1` と `project/generated/texture_cache/v1` です。生成テクスチャの計算式・サンプル数をエンジン側で変更するときは、`GeneratedTextureCache.h` のバージョンを上げて再生成させてください。ゲーム内エディターのブルーム強度・機体性能などの調整には、この操作は不要です。

## エンジンで今後分離するもの

今回の実測では、まず「このモードで使わない UI の生成を省く」と「毎回同じ結果になる計算を保存する」が有効でした。描画機能を一括して削除する必要はありません。

配布版をさらに詰める場合は、シェーダーのコンパイルや反射テクスチャの生成をビルド工程に移し、完成したデータを同梱する設計にできます。エディターでは変更時に再生成し、ゲーム側は完成データを読む構成です。DirectXTex にも DDS の読み書きが用意されています。[Microsoft の DDS I/O 資料](https://github.com/microsoft/DirectXTex/wiki/DDS-I-O-Functions)

一方、GPU 用のパイプライン状態（PSO）のキャッシュは GPU・ドライバーなどとの互換性管理が必要です。今回追加した計測で必要性を判断し、導入する場合も不一致なら作り直す方式が適切です。[Microsoft の PSO キャッシュ資料](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/ns-d3d12-d3d12_cached_pipeline_state)

シェーダーの依存ファイル検証には DXC の include ハンドラーを利用しています。[Microsoft の DXC Compile 資料](https://learn.microsoft.com/en-us/windows/win32/api/dxcapi/nf-dxcapi-idxccompiler3-compile)

## 検証結果

- Release / Development のビルド成功。
- `test_shader_disk_cache.ps1`: 実 DXC で保存・復元したバイナリーの一致、ソース／include／条件変更による無効化、破損、Unicode パス、利用不可保存先を検証。
- `test_generated_texture_cache.ps1`: 浮動小数点テクスチャの画素一致、キューブ・ミップ構造、破損・切断からの復旧を検証。
- `test_startup_trace.ps1`: 入れ子の時間集計、無効化、Unicode パス、保存失敗時の動作を検証。
- カード装飾の実際の生成処理 50,400 ケースで、最大 85/96 個の通常スプライト、28/32 個のグロースプライトに収まることを確認。既存カード挙動の検証も通過。
- `test_title_demo.ps1 -Configuration Release`: ４段階の戦闘、36 体の撃破、38 回のダッシュ、フェード中の固定、本編への初期状態での遷移を確認。以前の多重発射を要求していた検証条件は、現在の１砲門１発の仕様へ修正。
- `test_tank_experience_runtime.ps1 -Configuration Release -Route Upper -Style Melee`: チュートリアル、通貨回収、全レア度のカード表示、近接、強化保持、進化を確認。後半の戦闘は検証用に強制クリアしており、難易度の検証ではありません。

タイトルと機体系統選択・レジェンドカードの実機キャプチャも確認しました。
