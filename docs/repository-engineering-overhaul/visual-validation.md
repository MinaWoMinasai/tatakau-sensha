## 開始時と抽出後のNeon確認

開始HEADの固定baselineは`generated/repository-engineering-overhaul/baseline/test_neon_boss_runtime/`。Iteration 2時点のbinaryによる再確認は`generated/repository-engineering-overhaul/current-neon/runtime-project/generated/neon_boss_gameplay/`。両方を保存し、上書きしない。

同時点の13枚はIdle、Telegraph、実Volley後半、Dash、phase 2の既存2D／3D同状態pair 5組と、Dissolve 0／約0.5／1の3枚。各pairは同じworld／camera／simulation stateでfreezeし、描画選択だけ変える。PNG付属JSONにcamera matrix、Gameplay state、animation、Visual lifetimeを記録する。

全身の欠け、明らかな回転軸ずれ、独立したOutline、極端な白飛び、終端の人型残像はこのfixtureで見つからなかった。中間では脚側が残り、終端で人型とそのOutlineが消える。既存の撃破grayscale／grain、他actorやUIが残ることはDissolve残骸ではない。人型の四肢は円形colliderの外へ広がるため、大きさ・向きの自然さはユーザーの目視確認対象。

通常cameraを使うRelease combat fixtureの10枚は、開始HEADのPNGとSHA256がすべて一致した。この10例に限る証拠で、他GPUや全renderingの完全決定性には広げない。Rival／Dashの下端の欠け、phase 2の画面外ボスは開始HEADでも同じで、既存自機cameraとactor配置の関係によるもの。全身形状の確認はDeveloper中点cameraの13枚で行った。

根拠は`current-neon/visual-review.md`、`combat-capture-byte-comparison.json`、`run-manifest.json`、付属capture JSON。resourceは生成1回・死亡終端の解放1回・CB0。global descriptor差分だけから個別modelの解放数は判定しない。

## Scenarioによる撮影

新しいRunnerでは完了frameを指定し、snapshot・cameraをPNG付属JSONへ保存する。既存のcapture fenceと時間0の更新を使用し、撮影待ちで攻撃時計や位置を進めない。同じseed／script／capture frameの反復はGameplay state比較に使い、PNGの完全一致を必須にはしない。

入口の終了コード修正前のRunner画像は`final-validation/artifacts/test_gameplay_scenarios/run_20261004_221102_241_e67a04a2/`。rootはShooter frame360、Drone／Melee／ProjectileStress／EnemyStress frame120をPNGと付属camera／snapshotで確認した。Shoot／Drone companion／Melee slashと実敵、壁、UIが表示され、黒い全面欠落や明らかなtransform異常は見つからなかった。Droneの3体と2発、Meleeのactive attack1／敵HP49,942、ProjectileStressの実弾195、EnemyStressの64体という値は画像と同じframeのmetadataに残る。

stress画像は検証用の密な配置であり、通常playの見やすさやbalanceの評価には使わない。大量弾では局所的な黄色いglowが機体と重なり、64体の敵にはviewport上端で切れる個体もある。元のplayer-follow cameraとauthored roomを維持したfixtureのframing制約で、全64体が同時に画面へ入ることを要件にしない。

rootと別agentでRival／Prototype／Neonのframe360を確認した。RivalとNeonでは同じcamera／world anchorに2D円形bodyと人型が表示され、aimに対応する向きと一体のOutlineが見える。Prototypeは既存2D bodyと弾が表示される。Rival1とNeon1の全960frameについて、位置／HP／shot／phase等のGameplay observable 30項目をcanonical JSONで比較して一致した。証拠は`final-rival-neon-gameplay-comparison.json`で、descriptor／resource／CBとGPU時間は比較対象にしていない。

BossDeath1のframe121／165／201もrootと別agentがPNG／metadataを確認した。progress0では死亡姿勢と既存の局所impact発光、0.511111では脚側を残すDissolve、1では人型／Outlineと2D代替bodyが消えている。終端はHP0・dead、Visual生成1／解放1／CB0。撃破banner、grayscale／warp、通常敵やparticleは既存演出として残る。異なる撮影frame間にはcamera shakeがあり、完全に同じcameraの3画像と偽らず各camera matrixを記録する。stillだけで全depth接触を保証せず、MRT／Depthの終端は別の実GPU pipeline testで検証する。

このbinaryの既存Neon13枚は`final-validation/artifacts/test_neon_boss_runtime/`。別agentは全13枚、rootは3DのIdle／Telegraph／実Attack／Dash／low HPとDissolve3枚を確認した。Telegraph phase2、実Attack phase3・shot1、Dash phase5・dash1、HP300／900でphaseTwo、死亡後の位置／shot／Dash保持と生成1／解放1／CB0は同じPNGのmetadataで確認した。全身、aimによる向き、連続するOutlineが見え、明らかな欠落・90度の軸誤り・極端な生存時露出・終端の人型残像は見つからなかった。小さい人型や既存fallbackの姿勢の好みは手動確認へ残す。

rootはPlayerRestart／StageTransition／ExpeditionTransitionのframe360も確認した。restartはepoch2・HP120で通常の部屋を再表示し、Stageは実crossfireの壁／敵／弾を描画する。Expeditionはshop購入後、次のcombatへの「出撃」transition UIを表示する。frame360ではまだservice nodeであり、次room完了の根拠は画像だけでなく後続snapshot／terminal checkを用いる。

別agentの独立目視記録は`generated/repository-engineering-overhaul/visual-review-independent.md`。Scenario17枚と同binaryのNeon13枚、計30枚を実際に開いて確認した。Iteration 2の画像をこのbinaryの認証へ流用していない。旧driver内の設定probeはJSON key順を要求するtest側の問題で停止した。その後の修正とbinaryの区別は[final-validation.md](final-validation.md)で追い、さらに後の入口修正を含む新画像は次節に記録する。
