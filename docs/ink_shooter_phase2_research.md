# Ink Shooter Lab 第2段階：塗りパラメータ再調査と拡張設計

調査日：2026-09-12。基準は前段階と同じ **Splatoon 3 Ver.11.3.0、対戦用スプラシューター、能力補正なし**。この文書は追加調査と実装判断の区別を記録する。今回の変更点・最終採用値・実測結果は第2段階の実装報告を参照する。

## 維持するゲーム基準

連射6F、消費0.0092/発、回復停止20F、既存の弾速・減速・重力、地上/ジャンプ拡散、歩行/遊泳速度、タンク回復時間は維持する。録画30fpsをゲームの60Hz値の計測へ使わない。120Hz固定Simulationは原作のフレームレートを主張するものではなく、CG2の積分・入力処理の基準である。

前段階の根拠・共通初期値・単位変換は [ink_shooter_research.md](ink_shooter_research.md) にまとめている。距離縮尺 `S=0.5` は引き続きCG2独自の換算であり、実世界のメートル換算ではない。

## 意味が説明されている部分と未確認部分

[解析者XarrotD本人のパラメータ説明](https://splatoonwiki.org/wiki/User:XarrotD/paramtable) は、主着弾のDepthScaleを弾の進行方向への伸び係数と説明し、共通値 `DegreeUseDepthScaleMax=10°` と `DegreeUseDepthScaleMin=35°` の間で補間することを記載している。一方、BreakFreeの正確な働きは未確定と明記され、複数の飛沫項目も未解明として残っている。この説明ページは解析者の記録であり、任天堂の正式な実装仕様ではない。ページ本文の直接取得は403だったため、検索サービスに保存された同ページの本文を照合した。

実装上の判断：面法線を `n`、入射弾方向を `d` とした場合、面に対する角度は `asin(abs(dot(normalize(d), n)))` として求められる。面に沿う入射は0°、正面からの入射は90°。主方向は `d - dot(d,n)*n` を面に射影して得る。射影の長さがほぼ0なら面の接線を代用し、不安定な回転を防ぐ。この計算を床・坂・壁に共通適用するのはCG2の幾何設計である。

10°以下で最大、35°以上で最小、途中を補間する方針は説明に沿う。ただし、正対着弾をさらに丸くする補正、壁だけの倍率、BreakFree時の高さとの組合せ、輪郭の中心占有率・細い尾・ローブ配置は **CG2側の近似** と記録する。`WidthHalf` の数値だけから「その半径の完全な楕円を塗りつぶす」とは決められない。原作のブラシテクスチャ、輪郭のしきい値、塗り密度の公開定義は確認できなかった。

`SpawnNum=1.5` を平均頻度として消化すること、`SplitNum=8` に応じた8位相を自作すること、`[4]` を利用した足元救済条件を自作することには再現上の意味があるが、その完全な順序・配置・小数処理の一次資料を確認できていない。**「原作と同じ飛沫テーブルを実装した」とは報告しない。** `SpawnBetweenLength` を初回飛沫位置として流用せず、初回・途中・救済の条件を分ける。

## 第2段階への推奨と近似の表示

以下は公開値の変更ではなく、原作素材を使わず見た目を近づけるためのCG2独自設計案である。採用結果は実装報告で確定する。

| 役割 | 推奨する差別化 | 原作と断定しない部分 |
| --- | --- | --- |
| 主着弾 | 公開幅を基準に、入射方向へ長い中心と細い先端を持つ輪郭 | コア幅、ローブ配置、正対補正 |
| 途中の飛沫 | 主着弾より細く短い塗りで射線下をつなぐ | 位相表、小数の消化順、初速と重力 |
| 周囲の小粒 | 主塗りから離れた小さな範囲を散らす | 粒数、距離、乱数分布 |
| 足元救済 | 独立した条件で近傍の道を補助する | `[4]` の条件解釈、連射履歴の扱い |

見た目の輪郭をGPUだけ変更すると、自色の移動可否と塗りの境界が食い違う。楕円群の中心・長短半径・回転・所有者・面IDを共通スタンプにし、CPUとGPUの双方が同じ境界式を使う。マスク補間や画素単位のアンチエイリアスは表示用として追加できるが、離れた小粒を広い連続塗りへ変えるほどのぼかしは避ける。

## 任意のステージメッシュへ拡張する場合

今回の16枚の有限長方形方式を維持したまま、次段階で必要になる選択肢を比較する。以下はCG2向けの設計評価であり、Splatoonの方式を主張するものではない。

| 方式 | 利点 | 必要な追加と制約 |
| --- | --- | --- |
| メッシュごとの塗りテクスチャ | 現在の面IDをメッシュIDへ置き換えやすい。動く物体に追従可能 | 重複しない塗り専用UVが必要。オブジェクト数でメモリと管理数が増える |
| Mesh UV atlas | 全ステージの塗りを集約でき、画素密度を割り当てやすい | UV展開、島の余白、継ぎ目をまたぐスタンプ複製、島ごとの密度管理が必要 |
| Triangle ID + barycentric mapping | 衝突点から塗り座標を正確に復元できる | これだけでは保存先にならない。UV atlas等と組合せ、隣接三角形への広がりも処理する |
| Tiled world paint | 必要な領域のみ確保でき、現在のグリッド判定を分割しやすい | 同じXZにある橋・床・壁を区別する面層が必要。単純な上面投影では壁を扱えない |
| World-space virtual texture | 大規模な静的ステージで使用領域をページ単位管理できる | ページテーブル、割当て、更新順、継ぎ目、面方向/階層の識別が増え、今回の規模には重い |

次の小さな一歩は **三角形の衝突ヒットからメッシュID・三角形ID・重心座標・法線を返し、塗り専用UVへ写す** こと。その上でメッシュごとのテクスチャか小さなatlasを選ぶ。CPUは同じUVと共通スタンプで所有者を更新する。UV島を越える部分だけ隣接三角形へ再投影し、段階的に坂・角・壁の継ぎ目を検証する。

既存インターフェースは「有限面のUVへ変換」から「PaintSurfaceが塗り座標を返す」へ分離できる。弾道・所有者照会・描画が直接長方形に依存しないようにしておくと、飛沫生成やゲームの数値を変更せずに保存先を拡張できる。
